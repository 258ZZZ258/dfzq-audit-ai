## 一、六个结构性不足(现象 → 事故 → 根因)

### 1. SPEC 之前没有「约束装配」阶段 —— 最大的洞

**事故**:PR#39。SPEC-API 对着产品原型 V3 写,全程 grep `boundary/X-Internal-Token/perm_tags` **零命中**。然后 T1–T12 全落地、337 测试全绿、**四轮 Codex 审查通过**、合并——整条流水线运转完美,**但建错了东西**。
**根因**:你的 SDD 验证的是 *build the thing right*(建得对),没有任何一步验证 *build the right thing*(建对的东西)。SPEC 的输入面只有"需求来源"(原型),没有强制枚举**约束来源**:上游权威设计、跨仓冻结契约、这个交付物的**真实消费者是谁**(query-api 的消费者被假定为前端,实际是 audit-biz)。流程越自动化,这个洞越危险——agent 会以极高的执行力把错误规格完美实现。

### 2. 约束靠 agent 记忆,门靠人自觉 —— 昂贵的门迟早被跳

**事故**:PR#39 合并时,BGE-M3 集成门"用户决定跳过、直接合并"。
**规律**:任何**执行成本高**的门(要干净栈、要串行协调、要 6 小时)在时间压力下必然被跳;而**被跳过却无记录**的门等于不存在——你甚至无法事后盘点欠了多少债。这不是自律问题,是门的**经济学设计**问题。

### 3. 审查有代码维度,没有架构维度

**事故**:四轮审查、10 findings 全修——但全部是 per-diff 的代码质量/安全审查。**没有人审"这个 PR 是否符合系统拓扑/边界归属"**,而这恰是唯一致命的问题。
**根因**:Codex 的审查规则(`.cursor/rules/`)里没有"边界符合性"这个 checklist 维度(昨天我给 AGENTS.md 补了一条,但那只是补丁)。审查维度应该显式分层:正确性/安全(有)、架构/边界符合性(**无**)、文档-代码漂移(无)。

### 4. 知识与状态没有「刷新责任人」—— 一切记录都在悄悄过期

**事故清单**:biz 仓 CLAUDE.md 写着"HTTP 层尚未落地"而 PR#39 早已合并;我的 b-track 记忆停在"已合并 main ✅"仿佛完事,漂移 finding 已存在两天;devlog hook 写盘无人收编(问题 2);CLAUDE.md/AGENTS.md 本地副本无声失踪。
**根因**:你们有很好的**写入**纪律(devlog、回灌、指针),但没有**失效**机制——每份状态声明("已落地""待 X")都没有 owner 和触发器去更新它。文档腐烂不是被写错的,是被**时间**写错的。

### 5. 多人协作面靠口头,不靠仓库

**事故**:活分给同事,远端零 PR、零分支——任务传递走了口头通道,同事(和他的 agent)拿到的信息量不可控。更结构性的:CLAUDE.md/AGENTS.md gitignore 之后,**同事的 agent 拿到的项目规则 = 0**——你为"他可能不用 Claude"付出的代价是"他用什么都没有规则"。
**根因**:流程是为"**一个人 + 多 agent**"优化的,规则和任务都活在你的本机;"**多个人 + 各自的 agent**"要求**仓库本身携带流程**——工具无关的规范文档、Issue/DoR、PR 模板。

### 6. 共享可变资源没有租约

**事故**:audit-demo 栈被合并门会话 `down -v` 误删,2714 件语料 6–7 小时重跑。
**根因**:多 worktree 共享全局单例栈,协调靠"跑前确认对方空闲"的口头纪律。并行 agent 时代,**破坏性操作前的资源归属检查必须机械化**(锁文件/租约声明),不能靠会话自觉。

问得非常准——这正是预切块通道与自建通道的**责任边界**问题。诚实的回答是:**传统意义上的 QC(质量门)对 P-PRESEG 大部分确实失义了,但有一小块责任转移过来的"搬运质量"仍然是我们的**。拆开说:

## QC 七指标原本防的是"我们自己的错"

条款覆盖率/条号连续性/层级合法性/抽取充分性——防的全是 **S1 解析和 S3 建树的失真**(PDF 解析丢段、条款树错切、OCR 乱码)。语料来自甲方权威知识库、已按条切好时,这些失效模式**连同它们的检查一起消失**。这就是 SPEC 里 ①②③④⑦ 对 P-PRESEG 禁用的原因。

## 但有三类风险不随"源是权威的"而消失

1. **搬运损坏(我们的责任)**:源系统 → 导出 → 转换脚本 → intake,这条链上会出现编码损坏(GBK/UTF-8 mojibake)、截断、字段错位。乱码块一旦进 Milvus 会**污染向量空间**、且对外呈现为"源系统的内容"——错在我们,却让源背锅。指标⑥(文本质量)恰好是这类损坏的廉价哨兵。
2. **丢与多(我们的责任)**:导出 100 块、入库 98 块,没有任何指标会叫——这比"内容好不好"更要命,因为**覆盖缺口意味着用户在源系统能看到、问智能体却查不到**。这不是 S2 指标,是 **reconcile 式对账**(批次报告里 blocks 计数 ↔ chunks 计数)。
3. **源自身的数据质量(源的责任,我们无权修)**:元数据缺漏、字段不规范。关键在于:**红线是单向只读不回写,我们既不能修,拦截又会制造覆盖缺口**——把权威语料 QC_FAILED 挡在门外,等于替甲方决定"这条不算数"。所以这类只能**标记降级 + 批次报告**,不该做成门。

## 一句话结论

> **P-PRESEG 的 QC 从"质量门"降格为"搬运完整性哨兵":内容质量归源系统,搬运保真归我们。**

这对 T6 意味着一个具体调整(相对 SPEC §4 原设计):

- **保留为门**:仅 ⑥文本质量(乱码=搬运损坏,真该拦);
- **降为报告项**:"必填元数据完整率"从 QC 门降为批次报告 warning(源的元数据缺漏不拦,标记供人工决定是否找源侧补);
- **新增对账**:批次报告加 blocks↔chunks 计数核对(丢/多即红,这才是 preseg 最重要的"质检")。

对,就是这个结构——**甲方库是"上游源",我们的 PG 是"权威工作副本",Milvus 是"可丢弃的索引"**:

```
甲方知识库 ──SQL 只读拉取(批次+水位增量)──▶ 我们的 PG ──投影──▶ Milvus
   (上游源,从不回写)                    (权威快照,add-only)   (可随时从 PG 重建)
```

为什么中间这跳省不掉,四个硬理由:

1. **Milvus 的定位就是"可重建缓存"**(B2)。`rebuild`/冷备(`chunks.dense_vec_cold/sparse_vec_cold`)、`reconcile` 对账、幂等重跑,全部以**我们的 PG** 为根。重建时不能假设甲方库可达、权限仍在、数据没变——重建要的是"**当时入库的那份**",不是"甲方库现在的样子"。

2. **在线热路径不能依赖甲方库**。Milvus 里的 `text` 只有 2000 字截断,命中后的展示、引用回查、案例桥接反查(`cases` 表)全部回查 PG——如果没有自己的副本,每次用户提问都要打甲方库,等于把它拉进我们查询链路的可用性依赖,内网隔离/运维边界都不允许。

3. **时点快照语义**。查询智能体的回答要可追溯:"当时依据的是哪一版条文"。甲方库的行会被改、被删;我们这边 supersede 不删、版本链留痕,才能解释历史回答。这也是 D3(效力状态源权威+留痕)、自动 revise_replace 版本链的载体。

4. **管线机制全长在 PG 上**:幂等键、`import_batches` 回滚单元(B7)、meta_confirm 队列、QC 哨兵、批次对账——没有落库就没有这些抓手。

两个边界澄清,防止理解偏大:

- **不是整库镜像**。只拉检索需要的语料面(文档元数据+条款块+案例记录),按批次、按水位增量,幂等重跑安全;甲方库里的流程数据(如合规审查记录)不搬。
- **"维护"成本很低**。我们对这份 PG 没有编辑语义——它是 add-only 摄取快照,唯一的"维护"就是增量拉取+对账,数据错了修正方式永远是"源头改、重新拉"(单向只读红线的自然推论)。

所以准确说:**搬运的不是"库",是"入库时点的语料快照";PG 承担权威与审计,Milvus 只承担检索加速**。这套分工在现有管线里已经成立,preseg 只是把输入端从"文件解析"换成了"SQL 拉取"。
